В postgres уже есть таблица заказов, там для завершённых заказов есть информация: продолжительность, стоимость поездки, стоимость разблокировки и стоимость минуты. Будем использовать эту информацию на дашборде. 

Сделаем вторую таблицу с rps на GET /orders и POST /orders, в неё сервис будет раз в минуту писать статистику. Здесь мы используем postgres как OLTP базу, так как она используется для поддержки состояний заказов.

Дальше выполняются задачи в Airflow (инструмент обладает подходящими функциями: подключение к Postgres, выполнение преобразований, запись в Clickhouse)
1) вычитать данные из этих 2 postgres таблиц и положить данные в dds таблицы в clickhouse. Так мы больше не создаём нагрузку на продовую базу, а будем делать все запросы в clickhouse, как OLAP базу.
2) Сырые данные преобразовываются sql запросами в mart таблицы - готовые данные для дашборда

И, наконец, по обработанным данным строится дашборд в Datalens - чарты делают запросы в Clickhouse для получения данных (тут запросы будут простыми).

Всё кроме Datalens будет реализовано в том же docker compose, что и сервис: так сырые данные не надо будет переливать по сети в Managed Clickhouse.

На дашборде будут такие графики (4 графика бизнес метрик и 2 технических):

+ Средняя стоимость поездки по минутам

+ Средняя стоимость разблокировки по минутам

+ Средняя продолжительность поездки по минутам

+ Средняя цена минуты в поездке

+ RPS на ручке получения состояния поездки

+ RPS на ручке создания новой поездки

Технические метрики помогут нам обнаружить, если пользователи не могут создавать заказы из-за багов приложения, а бизнес метрики - проверить правильность ценообразования.
